# ODAC Agent Protocol (AGENTS.md)

Welcome, Agent. You are operating within the **ODAC** ecosystem. To maintain the integrity, performance, and scalability of this "Enterprise-Grade" platform, you must adhere to the following operational protocols.

## 1. Identity & Mindset
You are not just a coder; you are a **Distinguished Software Architect and Performance Engineer**.
- **Zero Debt**: Technical debt is unacceptable. Do it right the first time.
- **Sub-millisecond Focus**: Every cycle counts. Optimize for high throughput and low latency.
- **Enterprise Hardening**: Security and reliability are baked-in, not bolted-on.

## 2. The ODAC Architecture
ODAC is a single Go module (`odac`) producing six binaries, shipped as one Docker image.
- **Layout**: entry points live under `cmd/` (`odac` CLI, `odac-server` orchestrator, `odac-watchdog` supervisor, `odac-proxy`, `odac-dns`, `odac-mail` data plane); all shared code lives under `internal/`.
- **Boundaries**: the CLI talks to the server over the TCP API socket (`internal/apiproto`, 127.0.0.1:1453); the server drives the data-plane daemons over their unix-socket control APIs (`internal/dataplane`). Cross-binary contracts are pinned — never change a wire format casually.
- **Collaborators as interfaces**: packages depend on narrow interfaces (see `internal/appmgr`, `internal/hub`), wired together in `cmd/odac-server/main.go`. Follow that pattern; avoid global state.
- **Failure domains**: each data-plane binary is a separate OS process and therefore its own crash domain — a panic in `odac-mail` cannot take down the proxy, DNS, or the server. Reason about reliability at that granularity, never as "one panic kills the platform". The flip side: `internal/dataplane` respawns a dead daemon on the 1-second check tick with no backoff or retry ceiling, so a remotely triggerable panic degrades into a respawn loop — a full outage for that service that still reports healthy to the watchdog, because every probe hits a freshly started process.
- **HTTP/3 is the one web listener that does not overlap during an update.** TCP `:80`/`:443` and DNS share their ports through SO_REUSEPORT, but QUIC connection state lives in one process and the kernel routes by 4-tuple, so a shared UDP port sent about half of the old process's connections to a process that could not read them (7 of 12 in-flight downloads died, and the old process stayed up for the full 30s limit). `proxy.HTTP3Service` therefore binds without SO_REUSEPORT and retries until the old process releases the port. New HTTP/3 connections fail while the old process drains and clients use TCP for that window, which is why `/ready` does not track HTTP/3. Do not add SO_REUSEPORT back to this socket. `Alt-Svc` follows the same state: `proxy.setEdgeHeaders` sends it only on TLS responses while the service accepts connections, so a process waiting for the port or draining does not advertise a listener it cannot offer.
- **A proxy cache hit never passes through `ModifyResponse`.** Anything a response must carry has to survive that, which is why `restoreHeaders` reapplies the security defaults. `Alt-Svc` and HSTS go through `setEdgeHeaders` at each place a final response is produced (`ModifyResponse`, both cache hit paths, `errorHandler`) rather than once at the top of `ServeHTTP`, because `ReverseProxy` clears the writer's headers after forwarding a backend 1xx: an app that sent `103`, or any request with `Expect: 100-continue`, used to lose both. The caches keep an allowlist of headers (`Set-Cookie` must stay out of it), so a new policy header an app can send belongs in `replayedHeaders`. The body they store is always the raw one: both refuse `Content-Encoding` because they compress on serve and do not replay that header, and `cacheRecordWriter` drops the whole buffer past its limit because a partial body looks like a complete one to everything after it. A subdomain routes to its parent's app but is cached under its own name, and revalidation only acts on `200` and `304`, so a missed purge can keep serving removed content. Every purge therefore matches through `keyBelongsToHost`; the price is that a subdomain bound to a different app loses its cache when the parent deploys. A fetch that began before a purge must not store its result, or a removed asset or page comes back, so anything that stores a backend response reads `CacheManager.generation` before the fetch and writes through `storeUnlessPurged`. The lock in there is not optional: without it a store can pass its check, lose the CPU to the purge, and land after the walk that was meant to remove it. This relies on deploys calling `proxySync` before `proxyPurge`, so a fetch that starts after the purge reaches the new container.
- **The proxy forwards through `ReverseProxy.Rewrite`, never `Director`.** A Director runs before hop-by-hop removal, so a client naming `X-Real-IP` or the signed `X-Odac-Client-*` headers in `Connection` deleted what the director had just set, and `X-Forwarded-For` came out doubled. `Proxy.director` is still the one function that shapes an outbound request (`prepareRevalidation` calls it too), only its caller changed. WebSocket detection reads `Connection`/`Upgrade` as token lists (`isWebSocketUpgrade`), since Firefox sends `keep-alive, Upgrade` and the cache writers in front of a missed upgrade answered `502`. The TLS certificate cache is keyed by key pair (`certID`), not SNI, because `resolveDomain` sends any depth of unlisted subdomain to its parent: files load outside `p.mu` once per pair and the OCSP staple is fetched in the background.
- **The page cache is opt-in per response, but its failure modes are shared.** `ModifyResponse` keeps `X-Odac-Cache` only on a request marked with `pageRecordingKey`, because `cacheRecordWriter` is the only reader and every other path must strip it; deleting it unconditionally is what left the page cache silently off from the Go migration until this was fixed. A first observation (`pageEntry` candidate) stores only a hash because scanners hit endless URLs and an app may opt in from a catch-all route, and entries are immutable once stored so requests can read them without a lock. Pages may use at most half the shared budget since the asset cache cannot evict them. A bare `304` is not a withdrawal: only a `200` can remove a page.
- **Client certificates are enforced per request, per `Host`, not by the handshake.** The handshake (`Proxy.GetConfigForClient`) only decides whether to ask: a global request would prompt visitors of unrelated public sites. Everything that grants access lives in `Proxy.gateClientAuth` (`internal/proxy/proxy/clientauth.go`), which runs before the caches and hints because the SNI can name another host, a resumed session skips the chain check, and a connection outlives both its certificate and a revocation. A connection negotiated under another handshake (`handshake.key`: other rules, other issuers, or a silent host) gets `421`, which is also what sends a browser that coalesced two hosts back with the right SNI. `optional` uses `RequestClientCert` rather than `VerifyClientCertIfGiven` on purpose: the latter fails the handshake on an expired certificate, which would cost that visitor a public site. `ClientCAs` must never be nil, since crypto/tls reads that as "trust the host's roots".
- **An app with any mTLS host loses the parent walk on all its records.** `resolveDomain` sends any unlisted subdomain to its parent, and the framework routes on a Host's first label, so without this `admin.foo.x.com` reaches the `admin` route past `admin.x.com`'s policy. It is per app rather than per record because two records of one app reach the same code. `buildPayload` therefore gives every record of such an app an `mtls` entry, and its presence is what turns strict mode on: the proxy ignores payload members it does not know, so a forgotten field is a silently public site, which `TestClientAuthPayloadDecodesOnTheProxySide` pins. The table is installed before `UpdateConfig` so a domain gaining a policy is never reachable under the old rules.
- **Three things route around a client certificate policy, and they are handled differently.** A tunnel dials the backend directly, so `MTLS.Set`/`Issue` refuse an app with one and `buildPayload` drops the tunnel from the other direction: both doors, like host mode and domains. A published port and an unprotected sibling domain are legal and only warned about at `set`. App-facing `X-Odac-Client-*` headers are HMAC-signed because of the first two, plus `odac-network` neighbours: an app making a login decision on a bare header would believe anything that reaches it. The signing key is derived from `api.auth` per `mtls.AppIdentity` (never the container name, which a Blue-Green deploy changes), so nothing is stored or diffed, and it reaches the container only at start.
- **Certificate scope is server-side data, keyed by fingerprint.** A record's `hosts` is deliberately not inside the certificate, so a change needs no reissue and lands on the next request; serials are not the key because an external CA picks its own. `reauthorizeLive` re-runs the decision on in-flight requests at each push, and `ReverseProxy` closes an upgraded connection when its context ends, which is how a revocation reaches a WebSocket. A certificate from a managed CA with no record is refused rather than trusted, and `MTLS.Prune` runs on Domain's delete paths so a domain added again later is not opened by certificates from its previous life. The client's private key never reaches the server on the dashboard path: the browser holds it and `Issue` only reads a CSR's public key. A lost reply leaves the caller retrying with the same key, so `matchKey` returns what the request already produced, but a renewal may also keep its key and then one key has several records. A renewal therefore counts as a retry only through `renewedFrom`, map order must never pick the result, an expired certificate is never returned as a success, and a key is dead only once every record on it is revoked, since retiring the old certificate is the normal end of a renewal. That leaves a revoked certificate's renewal working on the same key, which is why `Revoke` names those in its reply.
- **An app may hold the client certificate actions only because their handler narrows them, per request.** `domain.mtls.cert.issue`, `revoke`, `list` and `import` were once denied to app tokens for their reach (minting past a policy on any domain), not for what they do, while `set` and `scope` stay denied for good. `api.Args.Caller` tells a handler who holds the token, and `domains.MTLS` keeps an app to the records whose `appId` is its token's name: every host of an issue is its own, a certificate is its own only if its CA is bound to one of its records *and* every host it opens is its own (a CA can be shared with another app's record), it never creates a CA, and it never revokes an unrecorded fingerprint, because that branch plants a revocation. Whatever it may not touch answers `not_found`, so a fingerprint cannot be probed. This is what lets an edge app like odac-tunnel certify devices for its own hosts. Do not move the check to grant time: a grant names no records, and a domain can move to another app after it. The zero `Caller` (a domain token, or a call site that forgot to fill it) reaches nothing, so a new path fails closed, and the hub passes `api.Operator` because it acts for the server's owner.
- **`domain.list` reports `mtls` as a view, never the stored object.** `mtlsListView` copies it under the config lock (the rows are encoded after the lock is released) and adds `external`, the subset of each `ca` list ODAC holds no key for, on the record and on each host override. A dashboard needs it because only an external CA lets a host be required with no certificate record. It is computed per reply and absent when empty, since the dashboard diffs these rows; never persist it, and never read a client-supplied one.
- **Asking is decided per host, and a per-host record is verified by hand.** `clientAuthTable.handshakeFor` sends a certificate request only on a required host, a host trusting an external CA, or a host some certificate in the pushed table opens; any other `optional` host is silent, keeps HTTP/3 and `Alt-Svc`, and serves anonymous 0-RTT (early data carrying a resumed identity still gets `425`). That is why the snapshot leaves expired certificates out: a scope the proxy holds makes its host ask. With `issuer: per-host` on a record, a single-host certificate is signed by that host's issuer (`CN=<host>, O=<CA name>`, `mtls.IssuerName`), which each server makes with its own key and keeps in `certStore` (`issuers` table, keys in `cert/mtls/issuers/`); the handshake names only that issuer, plus the CA when a certificate straight from it opens the host (`HostIssuer.Direct`). crypto/tls cannot verify such chains (another server's issuer has the same name and a different key), so a per-host handshake never verifies (`RequireAnyClientCert`) and `mtls.VerifyPerHost` decides per request: CA-signed, or an issuer with exactly this host's name, CA, pathlen 0, client auth, signed by the CA. The CA's own path length is enforced like any chain builder enforces it (`mtls.AllowsHostIssuer`): managed CAs are created with pathlen 1 so CA -> issuer -> leaf is a valid path everywhere, keychains included, and `set --issuer per-host` refuses a record or override whose CA has pathlen 0. Do not relax this by reading the CA as a bare trust anchor. The same function checks an import, which therefore needs the chain: a leaf from another server's issuer cannot be checked without it and is refused. A per-host certificate cannot be rescoped off its host, and a record cannot leave per-host mode while one is live, because record mode would refuse its chain.
- **A certificate import is a record, never a signature.** `domain.mtls.cert.import` is how a node learns a certificate another node signed with the shared CA (K18): it checks the chain the way the proxy will (`signingCA`, verifying at `NotBefore` when this clock is behind, since the proxy enforces the start on every request), requires a managed CA that every target host trusts, and stores the scope under Issue's rules. A revoked record, including an operator's tombstone for a fingerprint never seen, refuses the import, so a revocation that lands first is never undone. An app's revoke of an unknown fingerprint writes no tombstone (that would let it plant revocations), which means the order between an import and a revoke on a node is the caller's to keep: a dashboard must not send an import for a certificate it has started revoking.
- **A CA's private key enters only through `domain.mtls.ca.import`, on the local API.** It is how edge nodes share one managed CA, and the request carries the key, so the action is root-only twice over (`appDeniedActions`, and `ImportCA` refuses any caller that is not root) and is deliberately absent from the hub's command table: the Cloud never holds a CA key. CA ids are the first 16 hex of the certificate's SHA-256 for created, external and imported CAs alike, which is what makes the same CA line up across nodes; never derive one from anything per server. An external CA is not upgraded to managed by an import, since managed means every certificate needs a record and the ones it already issued have none. A CA leaves with its key, its issuers and its certificates (revocations stay, so a re-import cannot revive one): through `domain.mtls.ca.remove` (root-only and hub-less like the import), or when `MTLS.Set` drops it from the last trust list (`retireDroppedLocked`). That automatic path compares the trusted set before and after the change, so a CA imported and not bound yet is never taken, and it keeps any CA that still signed valid certificates, because a key cannot be brought back and a mistaken `--ca` must stay undoable.
- **Issued client certificates live in their own SQLite store, not in config.** `domains.certStore` (`cert/mtls/certs.db`) exists because a config module is rewritten whole under the lock every config reader takes, so one issue cost 1.27s of stalled server at 100k certificates. `config.mtls` keeps only the CAs. A push reads the store through `dataplane.ClientCertStore` before taking the config value lock, and a read failure reuses the last good snapshot: pushing nothing would lock out every `required` host, and pushing CAs with an empty revocation list would revive revoked certificates, so with no good copy at all the `mtls` member is left out and the proxy trusts nothing.
- **A certificate change does not take the `/config` path.** `/config` resets the proxy's TLS and OCSP caches for every site, so `Issue`, `Scope` and `Revoke` use `SyncClientCerts` and `/client-certs`, which replaces only the certificate table against the domains the proxy already has. Issuing under a new CA is the exception, because that writes `ca` onto a domain record. Anything but a `200` falls back to the full push, since a server can be newer than its proxy during an update. Both still send the whole table: at 100k certificates a change costs about 400ms of server and proxy CPU, though no request waits for it.
- **Verified chains are cached across pushes, in one bounded cache.** `verdictCache` belongs to the `Proxy`, not to a table. Its key hashes the trust anchors with the presented chain, so a change of CAs cannot reuse an answer while every other push keeps them; only verification lives there, because revocation and scope are read from the table on each request. It has two generations so a full cache costs only what went unused: resetting it whole put every client back through `x509.Verify` once more than 4096 certificates were active. `reauthorizeLive` evaluates outside `liveAuthMu` because every authenticated request takes that lock, and `trackLive` re-decides when the table moved between a request's decision and its registration, or a WebSocket opened in that gap would outlive a revocation.
- **Early hints are shared, so only the anonymous view may teach them.** `proxy.HintsStore` keys by host and path, and `Send` answers every client before the app has checked who is asking. `Learn` therefore accepts only an anonymous `GET` of the bare URL (no `Cookie`, `Authorization` or query, since a query can be a capability) with a shareable response (`cacheControlForbidsSharing`, `Set-Cookie`, `varyIsPersonal`). Credentialed, non-`GET` and query requests are ignored outright: letting them withdraw entries would make hints flap on any site with signed-in users. An anonymous non-`2xx` or personal response withdraws the entry, whatever its `Content-Type`; a JSON `401` that skipped this kept serving a signed-in user's `Link` to everyone until the TTL. `Send` must delete `Link` after writing the `103`, or the final response repeats it whatever its status. Entries are replaced, never edited, because `Send` reads them without a lock.
- **Mail storage is raw-first**: the verbatim RFC 5322 message is the record. `internal/mail/blob` keeps it content-addressed on disk (`~/.odac/mail/objects`, override `ODAC_MAIL_BLOB_DIR`) and `mail_received.rawRef` points at it; `internal/mail/mimetree` parses it into a part tree that carries byte offsets. IMAP answers `BODY[...]`, `RFC822` and `BODYSTRUCTURE` out of those offsets, so a part reaches the client exactly as transmitted. The `html`/`text`/`headers` columns are derived display data, never the source of truth: reconstructing a message from them is lossy and is what silently discarded every attachment before. Rows with no `rawRef` (pre-blob deliveries) still fall back to the synthesized `multipart/alternative`, so both paths must keep working.
- **`mail_received.attachments` is an index, never a container.** Each entry carries `partId` (an IMAP section path that round-trips through `mimetree.Resolve`) plus `offset`/`length` into the raw blob; the bytes stay in the message. The Node.js predecessor inlined content as a JSON array of byte values, inflating binary roughly 3.6x inside a column that `SELECT`s on the IMAP path pulled into memory. Do not add a content field back. `size`/`checksum` describe the decoded file, `length` the encoded bytes.
- **Both write paths go through `internal/mail/message`.** SMTP delivery and IMAP `APPEND` land in the same table, so `message.Parse` derives the display columns and `Parsed.Apply` maps them onto a `storage.MessageRow`, leaving only identity and placement (`Email`, `Mailbox`, `Flags`, `RawRef`) to the caller. Both store the verbatim bytes in the blob store first. `APPEND` used to dump the raw message into the `html` column instead, which lost every attachment on a saved draft and left the client no envelope to list it by, so a new path that writes mail belongs here rather than building a row of its own.
- **`mail_received.flags` is JSON that only the encoder may write.** Readers go through SQLite's `JSON_EACH`, which aborts the whole statement on a malformed value rather than skipping the row, so one bad value breaks `SELECT`, `EXPUNGE` and `STORE` for the entire mailbox. `storage.CanonicalFlags` and `storage.EncodeFlags` own the column's shape (lowercase, no leading backslash, JSON array) and every writer goes through them; every reader wraps the column in `safeFlagsExpr`. `APPEND` concatenating `(\Seen \Draft)` into `[\Seen` is what taught this.
- **Blob lifetime needs the sweeper.** Content addressing means a blob outlives the row that created it, so `blob.Sweeper` (started in `cmd/odac-mail/main.go`) walks the store and drops unreferenced objects older than a 24h grace period. The grace covers the window between writing a blob and committing its row; a failed reference lookup is always treated as "still referenced", because the opposite reading deletes live mail.
- **Outbound mail goes through a durable queue, `mail_outbound`.** Accepting a message and delivering it are separate steps: the transaction that answers `250` writes the mailbox copies and one queue row per remote recipient together (`storage.Store.Deliver`), so a failure is a `451` with nothing stored rather than a `250` for mail nobody holds. `smtp.Queue` (started in `cmd/odac-mail/main.go`) makes one attempt per row through `smtp.Client`, retries a temporary failure with backoff for five days, and on a permanent refusal or expiry stores an RFC 3464 bounce in the sender's INBOX; every sender is local, so a bounce never leaves the server. Rows are claimed with a lease in the database, never an in-memory set, because the old and new `odac-mail` run side by side during an update and both drain the queue; a stopped process hands its in-flight rows back unchanged. The message stays in the blob store under the row's `rawRef`, which is why `RawRefExists` also reads `mail_outbound`: a queued message outlives the sweeper's 24h grace. `mail.send` enqueues through the same path and answers once the row is stored, which is what lets its control call take the normal 30s bound. The client keeps no connection between deliveries: the pool it had handed one socket to concurrent senders and kept the plaintext socket after STARTTLS.
- **Kernel privilege is allowlisted, and absence is part of the contract.** `caps` (Linux capabilities) and `sysctls` travel on the app record and are validated by `internal/kernel`: the capability set is closed (nothing that crosses the container boundary, `SYS_ADMIN`/`SYS_MODULE` included) and sysctls are limited to the engine's namespaced set (`net.*`, `kernel.msg|sem|shm*`, `fs.mqueue.*`). Refusing at create matters because apps have their own respawn loop: `Manager.Check` restarts any active app whose container is not running on the 1-second pulse, so a request the engine rejects is not an error the operator sees, it is a container recreated every second. The allowlist here mirrors the Cloud's, it does not replace it. `Spec.Apply` writes the fields only when they carry something, and `ports` stamps `proto` only for UDP, because the dashboard diffs `app.list` rows by serialization and a cosmetic empty field marks every app on every server as changed.
- **Resource sizing is its own vocabulary, `internal/resources`.** `shmSize` (the container's `/dev/shm`, engine default 64 MiB) travels on the app record and is bounded, not allowlisted: 1 MiB to 64 GiB, accepted as `"512m"` or as a byte count, persisted as canonical bytes. It is deliberately not a third field on `kernel.Spec`, because caps and sysctls answer "may this container hold that slice of root?" while a size answers "how much?", and a memory or CPU limit belongs next to it rather than inside the privilege allowlist. `Spec.Apply` writes nothing when nothing was asked for, the same serialization-diff rule as `caps`. Apps sized this way are logged at container create: `/dev/shm` is a tmpfs the host's RAM backs, so an oversized one is host memory a container can take.
- **A GPU request has two axes, `internal/gpu`: which accelerator, and what happens without one.** `Runtime` may be pinned (`nvidia`/`rocm`/`intel`) or empty, meaning "whatever this host has"; `Optional` decides whether a host with nothing to give fails the create or falls back to the CPU. Required is the default and still refuses at `checkGPUHost`, because a CUDA-only image on the CPU crash-loops. Optional exists for the larger group of apps that accelerate when they can (transcoders, recorders), so it skips that pre-flight and is resolved per container create in `Manager.resolveGPU` (`internal/appmgr/gpu.go`) rather than once at create time: the request is persisted verbatim, so a host that gains or loses a card only needs a restart and `app.list` keeps serializing what the Cloud sent. Empty runtime is legal only together with `Optional`, since a required request that resolves to nothing has no honest outcome left. `Spec.Map` omits absent members, the same serialization-diff rule as `caps`.
- **The optional GPU fallback is what keeps a refusal from becoming an outage.** `Manager.startWithGPUFallback` retries a container once without the request when the daemon answers `docker.ErrGPUUnavailable` and the request was optional. The pre-flight asks the host, but the engine has the last word and can disagree; without the retry the start fails, `Manager.Check` recreates the container on the next 1-second pulse forever, and the watchdog still sees healthy because every probe hits a fresh process. A required request is never retried and never downgraded, so its failure reaches the app's build log in the daemon's own words.
- **GPU auto-detection ranks by capability, Intel last.** `sysinfo.gpuRuntime` prefers a registered `nvidia` engine runtime, then an answering NVIDIA driver, then AMD with `/sys/class/kfd`, then any Intel GPU with a DRM render node. The iGPU is a weak compute device but a real media engine, and the apps that genuinely need CUDA pin `nvidia` in their recipe and never reach the fallback. `ODAC_GPU_RUNTIME` accepts `intel` alongside `nvidia`/`rocm`/`none`, because a host whose `/sys/class/drm` ODAC's container cannot see has no other way to say so.
- **`app.list` reports the GPU request and the attachment as two different things.** The persisted `gpu` object is the request, echoed back the way the Cloud sent it; what a container actually holds is read from the engine (`docker.GPUAttachment`, filled by `GetStatus` off the inspect `List` already makes) and nested under `gpu.attached` by `gpuRow` (`internal/appmgr/gpu.go`). Nesting is the point: the Cloud may hand a row's `gpu` object straight back to `app.gpu`, and a resolved `vendor` written beside the request's own members would pin an auto reservation onto whatever card the host had that day. `attached` is absent rather than false when there is nothing, and rows with no `gpu` member never grow one, because a member that only says "no" is churn in a payload the dashboard diffs. `nodes` are the paths as passed (`/dev/dri`, not the `renderD*` the daemon expands it into); host card inventory belongs in `system.info`, not per app.
- **Host networking and `net.*` sysctls are kept apart at two doors**, the same shape as host-mode-vs-domains: a host-namespace container would configure the host's own network stack, so `Manager.SetNetworkMode` drops those sysctls (naming them in the reply) on the way to host mode, and `Client.kernelHostConfig` drops them again at container create for a hand-edited config. Capabilities are namespace-independent and survive both.
- **A bridge app's networks are a persisted list, and the proxy does not need `odac-network`.** ODAC runs in the host namespace, so the proxy reaches a container IP on any bridge; an app may leave `odac-network` (the default when the record has no `networks`), and that is how two routed apps are kept apart. An empty list means "share no network": `docker.PrivateNetwork` (`enable_icc=false`, not `internal`, so egress stays) is where it lands, and it is ODAC's placement, never the operator's, so no list may name it and `GetStatus` never reports it. Do not fold it into `odac-network-isolated`: that one blocks egress and lets its members reach each other, and isolated apps rely on both. On the app record a missing `networks` and an empty one differ (default vs private), and `toNetworks` keeps that as nil vs empty all the way to `RunOptions`. `docker.NormalizeNetworks` is the one check for both doors (`Manager.SetNetworks` and `RunApp` for a hand-edited record): it refuses `host`/`none`, since `host` there would bypass every `networkMode` guard. `RunApp` joins the extra networks before start so a green container never runs short of one, and the live path connects before it disconnects so a failure cannot strand a container with no address. A live change must `proxySync`: the proxy resolves IPs only on a sync, and the freed address can go to another app. `SetNetworks` never refuses an app another operation holds: the Hub's Save & Restart sends the list and `app.restart` together, and refusing there lost the list silently. It saves the record and `followNetworks` reconciles the container once the app is idle, without taking the processing lock (a standard restart drops it briefly before `run()`). The list is stored only when it differs from `[odac-network]`, the serialization-diff rule.
- **Native Builder**: use the internal builder (`internal/docker`). Do not introduce Nixpacks or other external builders.

## 3. Core Directives (Non-Negotiable)

### A. Performance & Scalability
- **Big-O Awareness**: Prioritize O(1) or O(n log n).
- **Concurrency Discipline**: goroutines must be tracked and stoppable; guard shared state; new tests must stay `-race` clean.
- **Memory Safety**: Close all streams, listeners, and connections. Prevent leaks at all costs.

### B. Engineering Standards
- **Toolchain Gates**: after ANY code modification run `gofmt -l .` (must print nothing), `go vet ./...` and `go test ./...` — all clean before you are done.
- **Structured Logging**: use the project's log helpers (module-prefixed lines; the watchdog adds timestamps). No stray `fmt.Println` in services.
- **Configuration**: NO HARDCODING. Use environment variables or the config store (`internal/config`). Ensure the system is "Zero-Config" where possible by inferring defaults.

### C. Security
- **Log Sanitation**: Mask sensitive data (passwords, tokens, secrets) before logging.
- **Hardened Inputs**: Sanitize and validate every input. Use secure execution patterns for shell commands.

## 4. Operational Workflow (The 4 Phases)

1.  **PHASE 0: ARCHITECTURAL PLAN**: Analyze the request. Check for existing helpers. Redesign if not scalable to 1 million users.
2.  **PHASE 1: IMPLEMENTATION**: Atomic, clean, and testable code behind narrow interfaces.
3.  **PHASE 2: STATIC ANALYSIS**: `gofmt` + `go vet`. Fix ALL findings. Exit code MUST be 0.
4.  **PHASE 3: VERIFICATION**: TDD approach. Write tests for edge cases first (`go test ./...`).
