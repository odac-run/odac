# ODAC Agent Protocol (AGENTS.md)

Welcome, Agent. You are operating within the **ODAC** ecosystem. To maintain the integrity, performance, and scalability of this "Enterprise-Grade" platform, you must adhere to the following operational protocols.

## 1. Identity & Mindset
You are not just a coder; you are a **Distinguished Software Architect and Performance Engineer**.
- **Zero Debt**: Technical debt is unacceptable. Do it right the first time.
- **Sub-millisecond Focus**: Every cycle counts. Optimize for high throughput and low latency.
- **Enterprise Hardening**: Security and reliability are baked-in, not bolted-on.

## 2. The ODAC Architecture
ODAC is a single Go module (`odac`) producing seven binaries, shipped as one Docker image.
- **Layout**: entry points live under `cmd/` (`odac` CLI, `odac-server` orchestrator, `odac-watchdog` supervisor, `odac-proxy`, `odac-dns`, `odac-mail` data plane, `odac-backup` per-job backup runner); all shared code lives under `internal/`.
- **The backup engine is linked into `odac-backup` alone.** The server starts it per job inside a helper container made from ODAC's own image, without `docker.sock`, and streams dump output to its stdin, so the engine's dependency tree and its failures stay out of every long-running process. `cmd/odac-backup/boundary_test.go` fails when another binary starts depending on it. Kopia is imported by `internal/backup/engine` only, and that wrapper exists to keep Kopia's zero values out: every snapshot is pinned (`pin`), because Kopia applies its default retention (keep 3 annual, 24 monthly, ...) by itself at every 45-minute upload checkpoint and would otherwise delete what ODAC's thinning keeps; maintenance runs with `SafetyFull` only (tests swap `maintenanceSafety`, nothing else may); and the connection file is written by `writeConnection` instead of `repo.Connect`, which opens the repository a second time to check the password and deletes the cache directory when that check fails.
- **The server talks to odac-backup through `internal/backup/proto`, which must never import the engine** (the boundary test checks it): the server links it, and the engine's types stay off the wire so an engine change cannot move it (`TestWireTypesMatchEngine` catches a field on one side only). A dump arrives framed and ends with a zero-length frame; never treat stdin EOF as the end, because a dump that died or a server that went away would then store a cut dump as a complete backup. The server starts the dump only on odac-backup's `ready` event, sent once the repository is open, so a wrong password or an unreachable target never opens a transaction in the database. Secrets travel in the header, never the environment, which `docker inspect` shows. Kopia's uploader ignores its context, so the engine wires cancellation to `Uploader.Cancel`; keep that, or `docker stop` reads on until some storage write fails. The protocol is versioned (`proto.Version`, `MinVersion` kept one release behind after a bump): new optional fields, operations and events stay within a version because receivers ignore what they do not know, and only a field whose being ignored would change the outcome bumps it. A helper runs the server's own image, so both sides normally match; the version is for the moments they do not.
- **Backup containers are started by `internal/backup/runner` through `internal/docker/backup.go`, and their containment is the point.** A helper runs ODAC's own image by id (`Client.SelfImage`, never the tag, which moves to the next release mid-update), with every capability dropped but the file ones a run needs, `no-new-privileges`, a read-only root, required memory (no swap past it) and pid limits, app directories mounted read-only and no network at all unless the repository is remote (then `BackupNetwork`, no inter-container traffic). A dump container runs the database app's image inside that app's network namespace with its entrypoint replaced, and always with logging off, since its stdout is the database's contents; a dump that exits non-zero never reads as EOF. Helper names start with `odac-bk-` because the updater owns `odac-backup` for the container it rolls back to. SMB and NFS targets are `local`-driver volumes created per helper and removed with it, because their options carry the password and `docker volume inspect` shows them; values with a comma are refused, since mount options are one comma-separated string. An I/O weight fails the container start on disks whose scheduler has none (most cloud disks), so `startAttached` retries once without it and stops asking. A helper outlives its server across an update: `Runner.Release` detaches instead of stopping, and the next server's `Adopt` replays followable helpers (backup, maintain, verify) from their `json-file` log. Adopt only after the handover, or both servers follow and remove the same helper; a stream restore is never followable, because its bytes would land in a log file on the host.
- **Backups reach the operator through `internal/backup/service` alone, one method per action, shared by the API and the Hub.** Every `backup.*` and `snapshot.*` action is closed to apps by namespace (`appDeniedNamespaces` in `internal/api/api.go`), because a target bind-mounts a host path (host root), a restore overwrites another app's data and a key opens every backup; an action added under those prefixes later is closed without touching the map. An API action and its Hub command share the name and the single object payload, and `registerBackupActions` (`cmd/odac-server/backup.go`) re-sends the Hub's `Triggers(action)` after a local change, so a change through either door reaches the dashboard. Finished runs and restores reach it through the manager's `OnRecord`/`OnRestore` hooks, which trigger the lists, and every `app.list` the app manager sends also re-sends `backup.coverage`. A key leaves only through `backup.key` (root caller only) and once through `backup.target.prepare`; `RestoreRequest.Key` is `json:"-"`, so the service reads it from the payload itself and it is never echoed or recorded. A restore without a mode is a new app, never in place. Staging ODAC's own state (`backup.server.*`) is on the local API only, never the Hub. On a server without backups the Hub keeps the commands (the table's order is pinned) but gives the lists no interval, so nothing pushes failures every few minutes. No `snapshot.*` action exists before the snapshot store does: an action that pretends to work is worse than none.
- **Thinning is calendar-anchored and path independent; keep it that way.** `internal/backup/thin` buckets backups into dyadic intervals aligned to the Unix epoch, each the largest one whose newest edge is at least `k` widths in the past, and keeps the oldest per bucket. Buckets then only merge, never shift, so thinning hourly and thinning once a year later delete the same backups (`TestThinningIsPathIndependent`). Buckets measured from `now` (age-relative) break that and delete more than the rule intends, since the manager thins incrementally. A job's newest backup is never deleted, and the unit of a decision is one job run, so an app and its linked database never come back from different moments. Space pressure must count garbage that maintenance has not returned yet (`Space.Garbage`): under `SafetyFull` a deleted snapshot's space comes back only after at least three full runs more than five hours apart, and re-deciding on the measured size alone deletes again for space already on its way back.
- **A shared filesystem target is divided by fair share, and no server ever deletes another's data.** Servers sharing a disk, SMB or NFS target have no protocol between them: maintenance and the space measurement run with `Request.Share`, which writes `<id>/usage.json` (size, garbage, time) and returns the other directories' files (`Space.Peers`). Writing it is a write, so it needs the owner claim; a clone stopped by the claim never overwrites it, and other machines' files are read only as small regular files, never through a symlink. A peer is active while its file is younger than `peerActive` (7 days); `thin.Space.floorShare` splits what the floor lacks (after every active server's garbage) among the active servers holding more live data than an even share, in proportion, so one at or below its share deletes nothing for another's growth. A stale peer is an orphan: its space stays counted as taken and only the operator removes it (`coverage.orphans`). The snapshot repository is never shared.
- **Verification runs in the maintenance slot and its damage warning is sticky.** `Manager.verify` holds `busy[target]` and `maintSlot` like maintenance, samples 5% of files on filesystem storage and 1% on S3 and WebDAV, weekly, and writes `targetState.Verifying` before the helper starts so the server that adopts it after an update records it (`adoptedVerify`). Damage sets `targetState.Corrupt` (coverage `corrupt`, snapshot warning `corrupt`), and only a later verification at 100% that finds nothing clears it, since a sample can miss the damaged file. New backups do not repair damage: Kopia deduplicates against the index, so the damaged content is never written again; repair is a manual Kopia step. Helper deadlines are on the manager's clock (`Manager.runContext` turns them into timeouts), never `context.WithDeadline` on an injected time.
- **Consistency is chosen per piece of data, and a dump's credentials reach it on stdin only.** `internal/backup/consistency` turns an app into a `Plan`: a recognized engine (the recipe's `backup.engine` or hook first, then the image name, verified by running the tool in the image the dump uses) gets a dump stream, and the volumes holding its data directory are `Covered`, left out of the file backup, because a live data directory read as files is torn; every other volume is files read live. Every dump and probe is a fixed `sh -c` wrapper (`fileScript`, `redisScript`) that turns stdin (`docker.DumpSpec.Stdin`) into a `0600` file in the dump container's tmpfs or one exported variable and then execs the tool with `/dev/null` as stdin; values reach the shell only as positional arguments, never as script text. Never move a secret into `Cmd` or `Env`: `docker inspect` shows both and `ps` on the host shows argv. A method that cannot be used (tool missing, no credentials, a Redis fork without memory for its copy-on-write pages) is a warning and its data falls back to files; only a probe that could not run (Docker down) is a `Plan` error, so a stalled daemon never turns a database into a torn file copy. MySQL bounds metadata lock waits through `loose-init-command` in its option file; MariaDB's dump ignores that, so its waits end only with the run's time limit. ClickHouse leaves frozen parts on the server: `Plan.Finish` must run after every run that called `Prepare`. Its parts directory exists only once `Prepare` has frozen them (`Dir.Prepared`), so `Manager.plan` must not check it and `preparedItems` drops it after `Prepare` only when nothing was frozen: checked at plan time, every ClickHouse backup and snapshot stored no MergeTree data and still reported ok.
- **`BackupDir` stores SQLite databases as copies from SQLite's online backup API, never as read.** `internal/backup/consistency/sqlitecopy` finds them by header and copies each in one backup step from a read-only connection (WAL readers never block writers; a rollback-journal database blocks them for the copy), into `engine.Config.ScratchDir` (default `<cache>/scratch`) only while the disk keeps `scratchReserve` free. The copy is stored under the live file's name, mode and owner but with its own mtime, because a WAL database's file keeps its mtime while the WAL takes the writes and Kopia reuses the previous content for an unchanged mtime and size. Its `-wal`, `-shm` and `-journal` are left out: next to the copy, a WAL from another moment would be replayed onto it when the restored database is opened, so an in-place restore must also delete the ones it finds. A database that cannot be copied falls back to the live copy.
- **The backup manager (`internal/backup`) is the only scheduler of backup work, and none of it rides the 1-second tick.** One goroutine schedules (it looks again at most every minute and is woken when a run or a deploy ends) and every run and maintenance is a tracked worker. One backup runs at a time per server and maintenance has its own slot; a target either of them holds is not touched by the other (`busy`), which is what keeps a backup and maintenance out of one repository. A job's next run time goes into `<base>/backup/state.json` when its run starts, so a run handed over in an update is not started again, and a run still marked running with no helper left at the next start runs again at once. The file is read again at every `Start`, because the server is built while the one it replaces still writes it. A Docker failure while inspecting or planning defers a run (retried after 5 minutes, never counted as failed), and a listing that fails deletes nothing.
- **Backups start after the handover and stop first.** `System.Init` starts them once `Updater.Init` has returned, never at ready, and `System.Stop` stops them before anything else. `Manager.Stop` releases the runner before it cancels, and every helper run gets a context of its own (`runContext`): a run that saw the cancel first would stop the helper the release meant to hand over. `Start` adopts before its first run and holds each adopted helper's target and slot until its result has been handled like a run of its own; the labels (`odac.backup.kind`, `job`, `target`, `apps`, `complete`, `finish`) carry what that takes. ClickHouse's frozen parts of a handed-over run are released by the next server, which plans the app again under the same run.
- **A deploy outranks a dump, and a dump is not taken twice.** The app manager reports its processing lock (`appmgr.DeployWatcher`); a dump whose app, or an app that links it, starts deploying is cancelled at once (`beginDump` checks and registers under one lock), and the rest of the run follows under the same run id once that group has been idle for two minutes (`followUp`, trigger `deploy`). Until then the run is partial: partial runs stay out of thinning and go once a newer complete run of their job exists, unless a follow-up still holds them, and a run's own marks are written before the tidy that follows it. A dump another job stored within `min(15m, every/4)` is read back through a restore helper (`Invocation.Source`) instead of dumping the database again; ClickHouse never is, since its parts are frozen per run. Nor is a dump stored before an app of its group was last deployed or held (`Manager.changed`, set by `DeployStarted` and `DeployEnded`, which a restore's `HoldApp` also reports) or before this manager started (`Manager.started`): the pre-restore safety dump was read back as the first backup after the restore, storing the data the restore had replaced as the newest point. `runner.Config.DumpIdle` (five minutes) ends a stream that delivers nothing while it is read, the only bound on MariaDB's metadata lock waits short of the run's limit (`clamp(4 x every, 1h, 12h)`); only time inside the source's `Read` counts, so a slow upload never trips it.
- **Space decisions are made after maintenance, on the engine's attribution.** A `usage` request with `Usage.Order` makes odac-backup walk every snapshot (`engine.Repo.Space`) and report the garbage and, for each prefix of a `thin.Squeeze` order, what deleting it frees for the repository and for that run's job; the manager deletes the shortest prefix that covers the floor (`thin.Space.Excess`, garbage counted) and each job's budget. The walk costs about what garbage collection costs, so it is made only when the floor or a budget is at stake or garbage was still coming back at the last measurement. Thinning, purges and partial cleanup run after every backup.
- **A restore never writes into live data, and only a commit gives up the data it replaced.** `Manager.StartRestore` (`internal/backup/restore.go`) takes the backup slot and the target like a backup (a waiting restore is overtaken by no backup or maintenance), holds every app it touches through `AppControl.HoldApp` (stopped, inactive and persisted so, which also reports a deploy to the dump logic) and restores each volume into a staging directory inside the volume itself, so every swap is a rename even when the volume is a mount point. The volume's own entries move into a keep directory and stay there until the whole restore, dump loads included, is committed. A volume emptied for a dump keeps them beside it instead (`volumeJob.keepBeside`: parent below the apps root, on the same file system, inside no other volume of the restore), because its database starts on it before the commit and postgres with `PGDATA` at the mount point (the image's default) refuses to initialize a directory holding the keep directory; only a volume that is a mount point of its own keeps them inside.; any failure before that puts every volume back and releases each app with the state it had. Each step is written to `<base>/backup/restore.json` before it starts (`restoreJournal`, phases per volume): a server that stops mid-restore (an update) abandons its holds and leaves the journal, and the next server rolls it back in `recoverRestore`, only after `Adopt`, so no helper of the previous server still writes into a staging directory. No new restore starts while a journal exists. Destinations are checked for symlinks below the apps directory (`checkPath`), and odac-backup's Kopia output refuses entry names that climb out, a path through a restored symlink and a name restored twice (`engine.guardedOutput`), because another server's repository is read in a migration. In place first stores the current state as a run of the reserved job `pre-restore` in this server's directory on the same target (refused, never skipped, unless `SkipSafety` is asked for); thinning has no policy for that job, so those runs stay until the snapshot store takes them over. Kopia's root `FinishDirectory` removes a `.kopia-entry` sibling of the target, which in a helper is the read-only root (EROFS, not ENOENT): the guard ignores exactly that.
- **A dump is loaded into a database its image initialized empty, with the engine's own client.** Before the app starts, the volumes under the engine's data roots (`consistency.DataVolumes`, the same roots a backup covers) are emptied (moved into the keep directory), so the entrypoint initializes from the app's environment and the dump is all the database holds; loading over existing tables would duplicate rows. `consistency.Shape` decides that while the app is stopped; `Planner.Load` needs the database running. Credentials reach the load on stdin ahead of the stream: `secretLinesScript` reads exactly that many lines with the shell's byte-at-a-time `read` into the tmpfs file and execs the tool on the rest, and `docker.DumpSpec.Input` closes the tool's stdin only when the stream ended with `io.EOF` (any other end kills the container), so a cut dump is never loaded as a whole one. Readiness must hold for ten seconds (`WaitReady`), because images run a temporary server to initialize (Mongo's listens on loopback). psql runs with `ON_ERROR_STOP=0` and its stderr is judged (`judgePostgres`): `pg_dumpall` recreates roles and databases the init made, anything else fails the restore. MySQL gets `FLUSH PRIVILEGES` after a dump of every database. Redis is not loaded but placed: its RDB goes to `dbfilename` in the emptied volume, owned like it, and, when the command line turns `appendonly` on, as `appendfilename` too (Redis then reads only the AOF; an RDB is a valid one and Redis 7 migrates it), with the 40-character end mark of a diskless transfer that `redis-cli --rdb -` leaves cut off (`RDBTrailerSize`), which Redis reads as a broken command in an AOF. ClickHouse replays its definitions (same UUIDs), then each frozen part is moved into `store/<p>/<uuid>/detached/` and attached by `ALTER TABLE ... ATTACH PART`. A hook's `restore` command gets the stream against the running app as it is.
- **A new-app restore shares nothing host-wide with the app it copies, and points the group at itself.** Each run stores every app's record as a `definition` snapshot (`addDefinitions`, env and therefore credentials included, encrypted in the repository), which is what lets an app deleted here, or one of another server, come back. `appmgr.CreateRestoredApp` drops published host ports (back to the proxy), host networking, devices and the API grant, gives every volume a directory under the new app (one outside the old app's directory goes to `volumes/<container path>`, never shared), copies recipe config files only when they are on this server, and renames the group: `env.linked`, and every env value naming an old app as a host (`RenameHosts`: the whole value, or after `@`, `//` or a list separator and before a port, path or separator), because a copy that kept an old name would write into the live app. Domains are records of their own and never follow. Git and script apps are restored in place only. An app keeps its name when it is free (a fresh server taking over), else gets `<name>-restored`.
- **ODAC's own state is staged by a running server and swapped in by the next start.** `StageServerRestore` refuses a server that has apps, restores `server-*` beside the live state under `<base>/backup/server-restore/<id>/` and writes `pending.json`; `ApplyServerRestore` runs in `odac-server`'s `main` before `config.Open`, sets the replaced directories aside, keeps this machine's `server` and `backup` modules (the watchdog rewrites `server` from its copy, and `backup` holds the targets the restore came through, whose owner sequence files stay here) and marks every restored app inactive until its data is restored in place. Each directory swapped is recorded first, so a start that dies in the middle finishes on the next one.
- **Snapshots are the manager's own repository, never a target, and they never hold up the operation that asked for them.** `internal/backup/snapshot*.go` keeps them in `<base>/backup/snapshots/repository` with a key in `key` beside it, made once through a hard link and never rewritten (a repository the key does not open can only be one whose key was lost, so it is started over); `SnapshotTarget` (`"snapshots"`, which no hex target id can be) is how restores, records and the dump reuse name it, and `Manager.access`/`observe` are the one switch between it and the settings, so every new caller of a target goes through them. It has a slot of its own beside the backup slot, so a deploy's snapshot never waits behind a remote backup; only its own maintenance and a restore from it hold it back. Its budget is the swap rule (`internal/system/diskbudget`, which swap also uses) above `thin.Floor`, with garbage counted as given back like the targets' space decisions; a snapshot is refused when its estimate (the series' last growth) does not fit and given up while writing when the disk nears the floor. A snapshot is whole or nothing: any failed piece deletes the run. The deploy's snapshot starts beside the build (`appmgr.Snapshotter`), is `exempt` (its own deploy neither defers it nor cancels its dump, and it never reuses a stored dump), and `PendingSnapshot.Wait` gives it up after a bounded wait: its dump must not run beside the migration the new container starts. The deploy goes on either way and is marked in `snapshot.status`. The safety copy before an in-place restore is a `pre-restore` snapshot, so with snapshots off such a restore needs `skipSafety`; the `pre-restore` runs older servers left on targets are thinned by `legacySafety`. Snapshot records, history and maintenance stay out of `backup.history` and `backup.status`, and `DeployStarted` cancels every registered dump (`Manager.dumps`), because a backup and a periodic snapshot can dump side by side.
- **A server's identity is `<base>/server-id`, not a config field.** `serverid.Ensure` creates it once through a hard link and never rewrites it; a corrupt file is an error, never a reason to mint a new id, because the id names the server's data on shared backup targets. It stays out of the `server` module on purpose: the watchdog and the server both rewrite that module whole from their own in-memory copies, so a stale copy could silently replace it.
- **A target holds one directory per server, and every write first claims it.** `internal/backup/settings` lays a target out as `<target>/<server id>/repository` (Kopia) with `server.json` next to it, and odac-backup's `engine.ClaimOwner` refuses any `Repo.Owner` claim whose storage does not name that layout. Before init, backup, delete or maintain, the helper reads `server.json` and fails with `owner_conflict` when it holds the claim's `Seq` or more (or another server id); otherwise it writes `Seq`. The server reserves each number durably before the run (`owners.next`, write-ahead), so it never sends one twice and a crash cannot make its own earlier write look like a clone. Those numbers live in `<base>/backup/owner/<target>.json`, never in the `backup` config module: a module is restored from `.bak` when damaged and the watchdog saves every module from its own copy at start, and either would hand back a number already sent. A conflict stops writes to that target until the operator runs `Adopt`, which is also how a target added again takes back its old directory. The check is not atomic across machines: two clones claiming in the same moment both pass once, and the one behind fails on its next write. `server.json` is written with plain file, S3 object and WebDAV calls rather than through Kopia's blob layer, whose filesystem and WebDAV storages shard names and add `.f`, which would hide the file from a person.
- **Backup settings never return a secret in a view.** Targets (with their key and storage credentials), jobs and snapshot settings live in the `backup` config module, which `settings.Settings` rewrites whole, as JSON, under its own mutex. Every list or view is a separate type with no secret fields at all (`TargetView`, `SMBView`, `S3View`, `WebDAVView`), filled by a JSON copy, so a secret cannot reach a list by accident. Only `Key` returns the key. A target is saved only after the operator confirms the key shown once (`PrepareTarget` then `ConfirmTarget`, pending entries in memory for 30 minutes) and after its init worked through the `Initializer` the manager provides. Its location (`kind` + address) cannot change later, because its backups are there, and two targets for one storage are refused, since they would keep two owner counters for one directory. A disk target is checked lexically (system trees, volatile trees, ODAC's base and host-root directories), because ODAC's container cannot see the host's file system. A job's target cannot change either, and a deleted job's backups are kept by default as `Retired` (no policy, so `thin.Thin` leaves them alone).
- **Boundaries**: the CLI talks to the server over the TCP API socket (`internal/apiproto`, 127.0.0.1:1453); the server drives the data-plane daemons over their unix-socket control APIs (`internal/dataplane`). Cross-binary contracts are pinned — never change a wire format casually.
- **Collaborators as interfaces**: packages depend on narrow interfaces (see `internal/appmgr`, `internal/hub`), wired together in `cmd/odac-server/main.go`. Follow that pattern; avoid global state.
- **Failure domains**: each data-plane binary is a separate OS process and therefore its own crash domain — a panic in `odac-mail` cannot take down the proxy, DNS, or the server. Reason about reliability at that granularity, never as "one panic kills the platform". The flip side: `internal/dataplane` respawns a dead daemon on the 1-second check tick with no backoff or retry ceiling, so a remotely triggerable panic degrades into a respawn loop — a full outage for that service that still reports healthy to the watchdog, because every probe hits a freshly started process.
- **HTTP/3 is the one web listener that does not overlap during an update.** TCP `:80`/`:443` and DNS share their ports through SO_REUSEPORT, but QUIC connection state lives in one process and the kernel routes by 4-tuple, so a shared UDP port sent about half of the old process's connections to a process that could not read them (7 of 12 in-flight downloads died, and the old process stayed up for the full 30s limit). `proxy.HTTP3Service` therefore binds without SO_REUSEPORT and retries until the old process releases the port. New HTTP/3 connections fail while the old process drains and clients use TCP for that window, which is why `/ready` does not track HTTP/3. Do not add SO_REUSEPORT back to this socket. `Alt-Svc` follows the same state: `proxy.setEdgeHeaders` sends it only on TLS responses while the service accepts connections, so a process waiting for the port or draining does not advertise a listener it cannot offer.
- **A proxy cache hit never passes through `ModifyResponse`.** Anything a response must carry has to survive that, which is why `restoreHeaders` reapplies the security defaults. `Alt-Svc` and HSTS go through `setEdgeHeaders` at each place a final response is produced (`ModifyResponse`, both cache hit paths, `errorHandler`) rather than once at the top of `ServeHTTP`, because `ReverseProxy` clears the writer's headers after forwarding a backend 1xx: an app that sent `103`, or any request with `Expect: 100-continue`, used to lose both. The caches keep an allowlist of headers (`Set-Cookie` must stay out of it), so a new policy header an app can send belongs in `replayedHeaders`. The body they store is always the raw one: both refuse `Content-Encoding` because they compress on serve and do not replay that header, and `cacheRecordWriter` drops the whole buffer past its limit because a partial body looks like a complete one to everything after it. A subdomain routes to its parent's app but is cached under its own name, and revalidation only acts on `200` and `304`, so a missed purge can keep serving removed content. Every purge therefore matches through `keyBelongsToHost`; the price is that a subdomain bound to a different app loses its cache when the parent deploys. A fetch that began before a purge must not store its result, or a removed asset or page comes back, so anything that stores a backend response reads `CacheManager.generation` before the fetch and writes through `storeUnlessPurged`. The lock in there is not optional: without it a store can pass its check, lose the CPU to the purge, and land after the walk that was meant to remove it. This relies on deploys calling `proxySync` before `proxyPurge`, so a fetch that starts after the purge reaches the new container.
- **The proxy forwards through `ReverseProxy.Rewrite`, never `Director`.** A Director runs before hop-by-hop removal, so a client naming `X-Real-IP` or the signed `X-Odac-Client-*` headers in `Connection` deleted what the director had just set, and `X-Forwarded-For` came out doubled. `Proxy.director` is still the one function that shapes an outbound request (`prepareRevalidation` calls it too), only its caller changed. WebSocket detection reads `Connection`/`Upgrade` as token lists (`isWebSocketUpgrade`), since Firefox sends `keep-alive, Upgrade` and the cache writers in front of a missed upgrade answered `502`. The TLS certificate cache is keyed by key pair (`certID`), not SNI, because `resolveDomain` sends any depth of unlisted subdomain to its parent: files load outside `p.mu` once per pair and the OCSP staple is fetched in the background.
- **The page cache is opt-in per response, but its failure modes are shared.** `ModifyResponse` keeps `X-Odac-Cache` only on a request marked with `pageRecordingKey`, because `cacheRecordWriter` is the only reader and every other path must strip it; deleting it unconditionally is what left the page cache silently off from the Go migration until this was fixed. A first observation (`pageEntry` candidate) stores only a hash because scanners hit endless URLs and an app may opt in from a catch-all route, and entries are immutable once stored so requests can read them without a lock. Pages may use at most half the shared budget since the asset cache cannot evict them. A bare `304` is not a withdrawal: only a `200` can remove a page.
- **Client certificates are enforced per request, per `Host`, not by the handshake.** The handshake (`Proxy.GetConfigForClient`) only decides whether to ask: a global request would prompt visitors of unrelated public sites. Everything that grants access lives in `Proxy.gateClientAuth` (`internal/proxy/proxy/clientauth.go`), which runs before the caches and hints because the SNI can name another host, a resumed session skips the chain check, and a connection outlives both its certificate and a revocation. A connection negotiated under another handshake (`handshake.key`: other rules, other issuers, or a silent host) gets `421`, which is also what sends a browser that coalesced two hosts back with the right SNI. `optional` uses `RequestClientCert` rather than `VerifyClientCertIfGiven` on purpose: the latter fails the handshake on an expired certificate, which would cost that visitor a public site. `ClientCAs` must never be nil, since crypto/tls reads that as "trust the host's roots".
- **An app with any mTLS host loses the parent walk on all its records.** `resolveDomain` sends any unlisted subdomain to its parent, and the framework routes on a Host's first label, so without this `admin.foo.x.com` reaches the `admin` route past `admin.x.com`'s policy. It is per app rather than per record because two records of one app reach the same code. `buildPayload` therefore gives every record of such an app an `mtls` entry, and its presence is what turns strict mode on: the proxy ignores payload members it does not know, so a forgotten field is a silently public site, which `TestClientAuthPayloadDecodesOnTheProxySide` pins. The table is installed before `UpdateConfig` so a domain gaining a policy is never reachable under the old rules.
- **Three things route around a client certificate policy, and they are handled differently.** A tunnel dials the backend directly, so `MTLS.Set`/`Issue` refuse an app with one and `buildPayload` drops the tunnel from the other direction: both doors, like host mode and domains. A published port and an unprotected sibling domain are legal and only warned about at `set`. App-facing `X-Odac-Client-*` headers are HMAC-signed because of the first two, plus `odac-network` neighbours: an app making a login decision on a bare header would believe anything that reaches it. The signing key is derived from `api.auth` per `mtls.AppIdentity` (never the container name, which a Blue-Green deploy changes), so nothing is stored or diffed, and it reaches the container only at start.
- **Certificate scope is server-side data, keyed by fingerprint.** A record's `hosts` is deliberately not inside the certificate, so a change needs no reissue and lands on the next request; serials are not the key because an external CA picks its own. `reauthorizeLive` re-runs the decision on in-flight requests at each push, and `ReverseProxy` closes an upgraded connection when its context ends, which is how a revocation reaches a WebSocket. A certificate from a managed CA with no record is refused rather than trusted, and `MTLS.Prune` runs on Domain's delete paths so a domain added again later is not opened by certificates from its previous life. The client's private key never reaches the server on the dashboard path: the browser holds it and `Issue` only reads a CSR's public key. A lost reply leaves the caller retrying with the same key, so `matchKey` returns what the request already produced, but a renewal may also keep its key and then one key has several records. A renewal therefore counts as a retry only through `renewedFrom`, map order must never pick the result, an expired certificate is never returned as a success, and a key is dead only once every record on it is revoked, since retiring the old certificate is the normal end of a renewal. That leaves a revoked certificate's renewal working on the same key, which is why `Revoke` names those in its reply.
- **An app may hold the client certificate actions only because their handler narrows them, per request.** `domain.mtls.cert.issue`, `revoke`, `list` and `import` were once denied to app tokens for their reach (minting past a policy on any domain), not for what they do, while `set` and `scope` stay denied for good. `api.Args.Caller` tells a handler who holds the token, and `domains.MTLS` keeps an app to the records whose `appId` is its token's name: every host of an issue is its own, a certificate is its own only if its CA is bound to one of its records *and* every host it opens is its own (a CA can be shared with another app's record), it never creates a CA, and it never revokes an unrecorded fingerprint, because that branch plants a revocation. Whatever it may not touch answers `not_found`, so a fingerprint cannot be probed. This is what lets an edge app like odac-tunnel certify devices for its own hosts. Do not move the check to grant time: a grant names no records, and a domain can move to another app after it. The zero `Caller` (a call site that forgot to fill it) reaches nothing, so a new path fails closed, and the hub passes `api.Operator` because it acts for the server's owner.
- **`mail.send` is narrowed per request the same way.** `dataplane.Mail.Send` takes `api.Args.Caller`: the operator sends as any configured domain, an app only as a domain whose record carries its `appId` (subdomains resolve to that record first), and the zero `Caller` as none. Another app's domain answers like an unknown one. The check lives in the handler for the same reason as the mTLS one: a grant names no domain, and a domain can move to another app after it.
- **No grant lets an app take a client certificate policy off a host.** `domain.mtls.set` is closed to apps, but `domain.delete` drops a record's policy and `Prune` its certificates, so delete plus add reopened a protected host. Three doors are therefore refused to any caller but the operator (the zero `Caller` included): `Domain.Delete` of a record carrying `mtls` or one of its subdomains, `Domain.Add` at or below another app's record carrying `mtls` (`underForeignPolicy`, wildcards by their base), since an exact record outranks the parent walk, and `Manager.Delete` of an app with such a record (`DomainDeleter.HasClientAuthPolicy`), whose cascade would do the same. Nothing else about these actions is narrowed: who may touch which app or domain is the operator's call at grant time. The hub and `DeleteByApp` pass `api.Operator`.
- **`domain.list` reports `mtls` as a view, never the stored object.** `mtlsListView` copies it under the config lock (the rows are encoded after the lock is released) and adds `external`, the subset of each `ca` list ODAC holds no key for, on the record and on each host override. A dashboard needs it because only an external CA lets a host be required with no certificate record. It is computed per reply and absent when empty, since the dashboard diffs these rows; never persist it, and never read a client-supplied one.
- **Asking is decided per host, and a per-host record is verified by hand.** `clientAuthTable.handshakeFor` sends a certificate request only on a required host, a host trusting an external CA, or a host some certificate in the pushed table opens; any other `optional` host is silent, keeps HTTP/3 and `Alt-Svc`, and serves anonymous 0-RTT (early data carrying a resumed identity still gets `425`). That is why the snapshot leaves expired certificates out: a scope the proxy holds makes its host ask. With `issuer: per-host` on a record, a single-host certificate is signed by that host's issuer (`CN=<host>, O=<CA name>`, `mtls.IssuerName`), which each server makes with its own key and keeps in `certStore` (`issuers` table, keys in `cert/mtls/issuers/`); the handshake names only that issuer, plus the CA when a certificate straight from it opens the host (`HostIssuer.Direct`). crypto/tls cannot verify such chains (another server's issuer has the same name and a different key), so a per-host handshake never verifies (`RequireAnyClientCert`) and `mtls.VerifyPerHost` decides per request: CA-signed, or an issuer with exactly this host's name, CA, pathlen 0, client auth, signed by the CA. The CA's own path length is enforced like any chain builder enforces it (`mtls.AllowsHostIssuer`): managed CAs are created with pathlen 1 so CA -> issuer -> leaf is a valid path everywhere, keychains included, and `set --issuer per-host` refuses a record or override whose CA has pathlen 0. Do not relax this by reading the CA as a bare trust anchor. The same function checks an import, which therefore needs the chain: a leaf from another server's issuer cannot be checked without it and is refused. A per-host certificate cannot be rescoped off its host, and a record cannot leave per-host mode while one is live, because record mode would refuse its chain.
- **A certificate import is a record, never a signature.** `domain.mtls.cert.import` is how a node learns a certificate another node signed with the shared CA (K18): it checks the chain the way the proxy will (`signingCA`, verifying at `NotBefore` when this clock is behind, since the proxy enforces the start on every request), requires a managed CA that every target host trusts, and stores the scope under Issue's rules. A revoked record, including an operator's tombstone for a fingerprint never seen, refuses the import, so a revocation that lands first is never undone. An app's revoke of an unknown fingerprint writes no tombstone (that would let it plant revocations), which means the order between an import and a revoke on a node is the caller's to keep: a dashboard must not send an import for a certificate it has started revoking.
- **A CA's private key enters only through `domain.mtls.ca.import`, on the local API.** It is how edge nodes share one managed CA, and the request carries the key, so the action is root-only twice over (`appDeniedActions`, and `ImportCA` refuses any caller that is not root) and is deliberately absent from the hub's command table: the Cloud never holds a CA key. CA ids are the first 16 hex of the certificate's SHA-256 for created, external and imported CAs alike, which is what makes the same CA line up across nodes; never derive one from anything per server. An external CA is not upgraded to managed by an import, since managed means every certificate needs a record and the ones it already issued have none. A CA leaves with its key, its issuers and its certificates (revocations stay, so a re-import cannot revive one): through `domain.mtls.ca.remove` (root-only and hub-less like the import), or when `MTLS.Set` drops it from the last trust list (`retireDroppedLocked`). That automatic path compares the trusted set before and after the change, so a CA imported and not bound yet is never taken, and it keeps any CA that still signed valid certificates, because a key cannot be brought back and a mistaken `--ca` must stay undoable.
- **Issued client certificates live in their own SQLite store, not in config.** `domains.certStore` (`cert/mtls/certs.db`) exists because a config module is rewritten whole under the lock every config reader takes, so one issue cost 1.27s of stalled server at 100k certificates. `config.mtls` keeps only the CAs. A push reads the store through `dataplane.ClientCertStore` before taking the config value lock, and a read failure reuses the last good snapshot: pushing nothing would lock out every `required` host, and pushing CAs with an empty revocation list would revive revoked certificates, so with no good copy at all the `mtls` member is left out and the proxy trusts nothing.
- **A certificate change does not take the `/config` path.** `/config` resets the proxy's TLS and OCSP caches for every site, so `Issue`, `Scope` and `Revoke` use `SyncClientCerts` and `/client-certs`, which replaces only the certificate table against the domains the proxy already has. Issuing under a new CA is the exception, because that writes `ca` onto a domain record. Anything but a `200` falls back to the full push, since a server can be newer than its proxy during an update. Both still send the whole table: at 100k certificates a change costs about 400ms of server and proxy CPU, though no request waits for it.
- **Verified chains are cached across pushes, in one bounded cache.** `verdictCache` belongs to the `Proxy`, not to a table. Its key hashes the trust anchors with the presented chain, so a change of CAs cannot reuse an answer while every other push keeps them; only verification lives there, because revocation and scope are read from the table on each request. It has two generations so a full cache costs only what went unused: resetting it whole put every client back through `x509.Verify` once more than 4096 certificates were active. `reauthorizeLive` evaluates outside `liveAuthMu` because every authenticated request takes that lock, and `trackLive` re-decides when the table moved between a request's decision and its registration, or a WebSocket opened in that gap would outlive a revocation.
- **Early hints are shared, so only the anonymous view may teach them.** `proxy.HintsStore` keys by host and path, and `Send` answers every client before the app has checked who is asking. `Learn` therefore accepts only an anonymous `GET` of the bare URL (no `Cookie`, `Authorization` or query, since a query can be a capability) with a shareable response (`cacheControlForbidsSharing`, `Set-Cookie`, `varyIsPersonal`). Credentialed, non-`GET` and query requests are ignored outright: letting them withdraw entries would make hints flap on any site with signed-in users. An anonymous non-`2xx` or personal response withdraws the entry, whatever its `Content-Type`; a JSON `401` that skipped this kept serving a signed-in user's `Link` to everyone until the TTL. `Send` must delete `Link` after writing the `103`, or the final response repeats it whatever its status. Entries are replaced, never edited, because `Send` reads them without a lock.
- **Mail storage is raw-first**: the verbatim RFC 5322 message is the record. `internal/mail/blob` keeps it content-addressed on disk (`~/.odac/mail/objects`, override `ODAC_MAIL_BLOB_DIR`) and `mail_received.rawRef` points at it; `internal/mail/mimetree` parses it into a part tree that carries byte offsets. IMAP answers `BODY[...]`, `RFC822` and `BODYSTRUCTURE` out of those offsets, so a part reaches the client exactly as transmitted. The `html`/`text`/`headers` columns are derived display data, never the source of truth: reconstructing a message from them is lossy and is what silently discarded every attachment before. Rows with no `rawRef` (pre-blob deliveries) still fall back to the synthesized `multipart/alternative`, so both paths must keep working.
- **`mail_received.attachments` is an index, never a container.** Each entry carries `partId` (an IMAP section path that round-trips through `mimetree.Resolve`) plus `offset`/`length` into the raw blob; the bytes stay in the message. The Node.js predecessor inlined content as a JSON array of byte values, inflating binary roughly 3.6x inside a column that `SELECT`s on the IMAP path pulled into memory. Do not add a content field back. `size`/`checksum` describe the decoded file, `length` the encoded bytes.
- **Both write paths go through `internal/mail/message`.** SMTP delivery and IMAP `APPEND` land in the same table, so `message.Parse` derives the display columns and `Parsed.Apply` maps them onto a `storage.MessageRow`, leaving only identity and placement (`Email`, `Mailbox`, `Flags`, `RawRef`) to the caller. Both store the verbatim bytes in the blob store first. `APPEND` used to dump the raw message into the `html` column instead, which lost every attachment on a saved draft and left the client no envelope to list it by, so a new path that writes mail belongs here rather than building a row of its own.
- **Inbound mail is screened only when the session has no login, and a screening failure is never evidence.** `internal/mail/spam` runs SPF, DKIM, DMARC, HELO and header checks inside `Session.Data` before the blob is written, so a refused message stores nothing and a delivered one carries the verdict. It prepends `Authentication-Results` and `X-Spam-Status` to the bytes it stores: that is one of two deliberate changes to the verbatim record (the winmail.dat expansion below is the other), because a header is what every mail client reads, and the sender's own copies are left in place rather than rewriting the message. Both SMTP ports get the screener, since port 465 accepts local delivery without a login too. Two things are refused (`550 5.7.1`, so the sending server, not ODAC, tells the sender, which keeps ODAC from producing backscatter): a DMARC `p=reject` failure, a message whose envelope sender or `From` is on a local domain without an SPF or DKIM pass for that domain (whatever DMARC the domain publishes, since a domain whose DNS lives elsewhere may publish none and an impersonation with the attacker's own SPF pass then scored below Junk), and a message whose envelope sender or `From` is a local account, whatever SPF and DKIM say, because a local account sends only through an authenticated session (`WithAccounts`). A failed account lookup answers `451` instead, and so does a refusal whose missing pass may be hidden behind an SPF or DKIM temperror (`evaluation.pending`). Everything else is scored into INBOX or Junk. A DNS timeout or temperror adds nothing, and `Filter.Check` recovers a parser panic into the unscreened verdict: either failure turned into "spam" would make a stalled resolver or one crafted message cost every delivery, and a panic here is a remotely triggerable `odac-mail` respawn loop. `ODAC_MAIL_SPAM` (`enforce`/`junk`/`tag`/`off`) is the operator's escape hatch from false positives.
- **A winmail.dat is expanded for local mailboxes, and the message as received is kept beside it.** Outside Outlook an `application/ms-tnef` part is one opaque file, so `Session.Data` hands the screened bytes to `winmail.Expand`, which splices each TNEF part (`internal/mail/tnef` decodes it) into ordinary MIME parts and prepends `X-Odac-Tnef: converted`; every other byte stays where the sender put it. This is the second deliberate change to the verbatim record, so the original is never given up for it: the converted copy is `rawRef`, the screened original is `originalRef`, a conversion is used only once both blobs are stored, `RawRefExists` counts `originalRef` as live and `MessageCopy` carries it. Only local recipients' rows are converted: the Sent copy and the queue keep what the sender wrote, since a remote server reads TNEF on its own terms. It fails open twice over: `tnef.Decode` returns the whole stream or an error, never part of it, and any error delivers the message unchanged, because a winmail.dat that stays is better than an attachment that silently disappears. Only the `IPM.Note` family is converted; a meeting request or a receipt would lose its meaning as MIME and is left for Outlook. The stored copy's DKIM signature no longer verifies, which nothing checks after screening; a future forwarding or export path must send `originalRef`, not `rawRef`. Both packages parse untrusted input in `odac-mail`, so they recover panics like the spam filter and are fuzzed through unrecovered variants (`decode`, `expand`). `ODAC_MAIL_TNEF=off` turns it off.
- **`mail_received.flags` is JSON that only the encoder may write.** Readers go through SQLite's `JSON_EACH`, which aborts the whole statement on a malformed value rather than skipping the row, so one bad value breaks `SELECT`, `EXPUNGE` and `STORE` for the entire mailbox. `storage.CanonicalFlags` and `storage.EncodeFlags` own the column's shape (lowercase, no leading backslash, JSON array) and every writer goes through them; every reader wraps the column in `safeFlagsExpr`. `APPEND` concatenating `(\Seen \Draft)` into `[\Seen` is what taught this.
- **Blob lifetime needs the sweeper.** Content addressing means a blob outlives the row that created it, so `blob.Sweeper` (started in `cmd/odac-mail/main.go`) walks the store and drops unreferenced objects older than a 24h grace period. The grace covers the window between writing a blob and committing its row; a failed reference lookup is always treated as "still referenced", because the opposite reading deletes live mail.
- **Outbound mail goes through a durable queue, `mail_outbound`.** Accepting a message and delivering it are separate steps: the transaction that answers `250` writes the mailbox copies and one queue row per remote recipient together (`storage.Store.Deliver`), so a failure is a `451` with nothing stored rather than a `250` for mail nobody holds. `smtp.Queue` (started in `cmd/odac-mail/main.go`) makes one attempt per row through `smtp.Client`, retries a temporary failure with backoff for five days, and on a permanent refusal or expiry stores an RFC 3464 bounce in the sender's INBOX; every sender is local, so a bounce never leaves the server. Rows are claimed with a lease in the database, never an in-memory set, because the old and new `odac-mail` run side by side during an update and both drain the queue; a stopped process hands its in-flight rows back unchanged. The message stays in the blob store under the row's `rawRef`, which is why `RawRefExists` also reads `mail_outbound`: a queued message outlives the sweeper's 24h grace. `mail.send` enqueues through the same path and answers once the row is stored (a local account among its recipients gets its mailbox row in that transaction instead of a queue row: queued, it would loop through this server's own MX onto port 25 unauthenticated, where the spam filter refuses a local-account sender as forged), which is what lets its control call take the normal 30s bound. The client keeps no connection between deliveries: the pool it had handed one socket to concurrent senders and kept the plaintext socket after STARTTLS.
- **Kernel privilege is allowlisted, and absence is part of the contract.** `caps` (Linux capabilities) and `sysctls` travel on the app record and are validated by `internal/kernel`: the capability set is closed (nothing that crosses the container boundary, `SYS_ADMIN`/`SYS_MODULE` included) and sysctls are limited to the engine's namespaced set (`net.*`, `kernel.msg|sem|shm*`, `fs.mqueue.*`). Refusing at create matters because apps have their own respawn loop: `Manager.Check` restarts any active app whose container is not running on the 1-second pulse, so a request the engine rejects is not an error the operator sees, it is a container recreated every second. The allowlist here mirrors the Cloud's, it does not replace it. `Spec.Apply` writes the fields only when they carry something, and `ports` stamps `proto` only for UDP, because the dashboard diffs `app.list` rows by serialization and a cosmetic empty field marks every app on every server as changed.
- **Resource sizing is its own vocabulary, `internal/resources`.** `shmSize` (the container's `/dev/shm`, engine default 64 MiB) travels on the app record and is bounded, not allowlisted: 1 MiB to 64 GiB, accepted as `"512m"` or as a byte count, persisted as canonical bytes. It is deliberately not a third field on `kernel.Spec`, because caps and sysctls answer "may this container hold that slice of root?" while a size answers "how much?", and a memory or CPU limit belongs next to it rather than inside the privilege allowlist. `Spec.Apply` writes nothing when nothing was asked for, the same serialization-diff rule as `caps`. Apps sized this way are logged at container create: `/dev/shm` is a tmpfs the host's RAM backs, so an oversized one is host memory a container can take.
- **A GPU request has two axes, `internal/gpu`: which accelerator, and what happens without one.** `Runtime` may be pinned (`nvidia`/`rocm`/`intel`) or empty, meaning "whatever this host has"; `Optional` decides whether a host with nothing to give fails the create or falls back to the CPU. Required is the default and still refuses at `checkGPUHost`, because a CUDA-only image on the CPU crash-loops. Optional exists for the larger group of apps that accelerate when they can (transcoders, recorders), so it skips that pre-flight and is resolved per container create in `Manager.resolveGPU` (`internal/appmgr/gpu.go`) rather than once at create time: the request is persisted verbatim, so a host that gains or loses a card only needs a restart and `app.list` keeps serializing what the Cloud sent. Empty runtime is legal only together with `Optional`, since a required request that resolves to nothing has no honest outcome left. `Spec.Map` omits absent members, the same serialization-diff rule as `caps`.
- **The optional GPU fallback is what keeps a refusal from becoming an outage.** `Manager.startWithGPUFallback` retries a container once without the request when the daemon answers `docker.ErrGPUUnavailable` and the request was optional. The pre-flight asks the host, but the engine has the last word and can disagree; without the retry the start fails, `Manager.Check` recreates the container on the next 1-second pulse forever, and the watchdog still sees healthy because every probe hits a fresh process. A required request is never retried and never downgraded, so its failure reaches the app's build log in the daemon's own words.
- **GPU auto-detection ranks by capability, Intel last.** `sysinfo.gpuRuntime` prefers a registered `nvidia` engine runtime, then an answering NVIDIA driver, then AMD with `/sys/class/kfd`, then any Intel GPU with a DRM render node. The iGPU is a weak compute device but a real media engine, and the apps that genuinely need CUDA pin `nvidia` in their recipe and never reach the fallback. `ODAC_GPU_RUNTIME` accepts `intel` alongside `nvidia`/`rocm`/`none`, because a host whose `/sys/class/drm` ODAC's container cannot see has no other way to say so.
- **`app.list` reports the GPU request and the attachment as two different things.** The persisted `gpu` object is the request, echoed back the way the Cloud sent it; what a container actually holds is read from the engine (`docker.GPUAttachment`, filled by `GetStatus` off the inspect `List` already makes) and nested under `gpu.attached` by `gpuRow` (`internal/appmgr/gpu.go`). Nesting is the point: the Cloud may hand a row's `gpu` object straight back to `app.gpu`, and a resolved `vendor` written beside the request's own members would pin an auto reservation onto whatever card the host had that day. `attached` is absent rather than false when there is nothing, and rows with no `gpu` member never grow one, because a member that only says "no" is churn in a payload the dashboard diffs. `nodes` are the paths as passed (`/dev/dri`, not the `renderD*` the daemon expands it into); host card inventory belongs in `system.info`, not per app.
- **Host networking and `net.*` sysctls are kept apart at two doors**, the same shape as host-mode-vs-domains: a host-namespace container would configure the host's own network stack, so `Manager.SetNetworkMode` drops those sysctls (naming them in the reply) on the way to host mode, and `Client.kernelHostConfig` drops them again at container create for a hand-edited config. Capabilities are namespace-independent and survive both.
- **A bridge app's networks are a persisted list, and the proxy does not need `odac-network`.** ODAC runs in the host namespace, so the proxy reaches a container IP on any bridge; an app may leave `odac-network` (the default when the record has no `networks`), and that is how two routed apps are kept apart. An empty list means "share no network": `docker.PrivateNetwork` (`enable_icc=false`, not `internal`, so egress stays) is where it lands, and it is ODAC's placement, never the operator's, so no list may name it and `GetStatus` never reports it. Do not fold it into `odac-network-isolated`: that one blocks egress and lets its members reach each other, and isolated apps rely on both. On the app record a missing `networks` and an empty one differ (default vs private), and `toNetworks` keeps that as nil vs empty all the way to `RunOptions`. `docker.NormalizeNetworks` is the one check for both doors (`Manager.SetNetworks` and `RunApp` for a hand-edited record): it refuses `host`/`none`, since `host` there would bypass every `networkMode` guard. `RunApp` joins the extra networks before start so a green container never runs short of one, and the live path connects before it disconnects so a failure cannot strand a container with no address. A live change must `proxySync`: the proxy resolves IPs only on a sync, and the freed address can go to another app. `SetNetworks` never refuses an app another operation holds: the Hub's Save & Restart sends the list and `app.restart` together, and refusing there lost the list silently. It saves the record and `followNetworks` reconciles the container once the app is idle, without taking the processing lock (a standard restart drops it briefly before `run()`). The list is stored only when it differs from `[odac-network]`, the serialization-diff rule.
- **Docker is never asked under the config write lock, and a probe that fails is "unknown", not "stopped".** Every `cfg.View` (API authentication, autosave, the app pulse) waits on `cfg.Mutate`, so `Proxy.syncConfig` resolves container addresses first (`resolveContainerIPs`, once per container, within a time budget) and only builds the payload under the lock. `Manager.Check` rides the 1-second tick that also drives the data-plane supervisors, so it reads liveness from one bounded `RunningNames` list per pulse rather than an inspect per app, and skips the pulse when the list fails: reading a stalled daemon as "every app stopped" recreated them all. State probes in `internal/docker` carry `probeTimeout`, because the SDK sets no deadline of its own.
- **Native Builder**: use the internal builder (`internal/docker`). Do not introduce Nixpacks or other external builders.
- **Builder images come from floating tags, so they are refreshed on every build.** `EnsureImage` pulls only a missing image, which kept a cached `golang:1.26-alpine` on 1.26.10 forever and failed every `go 1.26.11` module under `GOTOOLCHAIN=local`. The compiler image, the runtime base and a custom Dockerfile's `FROM` images therefore go through `RefreshImage`, which falls back to the local copy when the registry is unreachable or rate-limited; `docker build` reuses a local base as is (verified), so refreshing only the compiler is not enough. `EnsureImage` stays right for digest-pinned images (`gitImage`, `packagerImage`) and for app images, where a restart must not upgrade silently. Node, Bun and Python run on their compiler image (`packageSpec.baseImage` empty), because a native addon or wheel only loads on the version that installed it; PHP's version picks the runtime (`php:<v>-apache`) and never the `composer` tag, which follows Composer's own versions.
- **Build steps run in a sandbox, never on the host's network stack.** The compile step runs every install script of every dependency, so `sandboxHostConfig` puts it and the git sandbox on `docker.BuildNetwork` (a bridge with egress and `enable_icc=false`), drops every capability but the file and uid ones package managers need as root, sets `no-new-privileges` and a `PidsLimit`. Host networking was the old setting and is what to avoid: it let a build reach the API on `127.0.0.1:1453` and every app on every bridge, and a root process there may join the proxy's `SO_REUSEPORT` groups on `:80`/`:443`, since Linux admits a socket with the same effective uid. The token reaches git only through an env-configured credential helper (`credentialEnv`), never the remote URL, because `.git/config` is readable by the compile step and copied into a custom Dockerfile's image. Files the server writes into or reads from the source tree go through `writeBuildFile` and `readProjectFile`: the tree is written by repository code, so a committed symlink must not redirect a write or point a read at `/dev/zero`. `gitImage` and `packagerImage` are pinned by digest because one receives the token and the other the Docker socket; bump them by digest.
- **The directory mounted at `/odac` holds `api.sock` and nothing else.** Apps with an API grant get `run/` (`rundir.App`) bind-mounted read-only, and a read-only mount does not stop `connect()` on a socket inside it. The data-plane control sockets used to live there, so a root app could replace the whole proxy config (verified against a real `odac-proxy`), reach mail past `mail.send`'s narrowing, or drive an update handover. Control sockets, their PID files and `update.sock` live in `rundir.Control`, a `0700` sibling that is never mounted. A private subdirectory of `run/` is no substitute, because root in a container keeps `CAP_DAC_OVERRIDE`. `api.sock` stays where it is: running containers see the directory live and would lose the API until restarted. For one release the supervisor still adopts orphans from `run/` (`LegacyRunDir`) and the updater still handshakes there (`legacySocketPath`); remove both after that. A downgrade across this change loses the zero-downtime handover, since the older release looks only in `run/`.
- **The proxy dials an app's unix socket pinned, never by name.** The app creates the socket in a directory it can write, so it controls the name, and the ODAC container holds `docker.sock`: a plain `connect()` follows a symlink and would hand that app's public traffic to the Docker API. `dialPinned` (`internal/proxy/proxy/pinned_linux.go`) opens each component with `O_NOFOLLOW`, requires `S_IFSOCK` on the final inode and connects through `/proc/self/fd`, so the name is resolved once. A record's `socket` is honoured only as `<root>/<dir>/<name>` under `ODAC_BACKEND_SOCKET_DIR`, which comes from the environment, not the config payload. Every failed socket dial falls back to TCP on the same request (`backendAddr` is both the fallback address and the routing key, so all forwarding paths derive their URL host from it), and each socket gets its own `http.Transport` so idle pools never mix. Other platforms stay on TCP.
- **The proxy signs the connection headers, because a private peer proves nothing.** A published port and a neighbour on a shared network both reach an app's TCP port, so `X-Odac-Connection-RemoteAddress`/`-Ssl` are covered by `X-Odac-Connection-Signature` (`internal/proxysig`), HMAC-SHA256 over method, Host, request URI and both values, with the key `mtls.AppKey` already derives per `mtls.AppIdentity`. Every app gets it as `ODAC_PROXY_KEY` at start (`Manager.injectProxyKeys`), and every routed record carries it as `key`; no key is derived when `api.auth` is empty. One key serves this and the client certificate signature, so the signed strings must keep distinct first lines (`odac-connection-v1` vs `v1`). The signed string and its test vector are mirrored in the framework (`src/Request/TrustedProxy.js`) and in `docs/server/07-proxy/03-app-integration.md`: change all three or none. Do not move to the RFC 9421 `Signature` header: ActivityPub apps verify their own `Signature` end to end. Tunnels are signed by the agent: ODAC Cloud reports the visitor's address and TLS state in the same two headers, and the agent dialed it over verified TLS, so `serveTunnel` answers the yamux session as HTTP instead of piping bytes, carries those two values over and signs them through the same `setConnectionHeaders` the proxy uses. Never go back to a raw pipe: an unsigned tunnel leaves the app trusting either nobody's headers (visitors look like the bridge gateway) or anybody's.
- **A container's socket directory is named once and read back from the engine.** `Manager.attachProxySocket` gives each bridge git/container app a fresh `rundir.Backends` subdirectory named after the container at create, mounted at `rundir.BackendMount` with `ODAC_PROXY_SOCKET` pointing into it. A Blue-Green green container is renamed to the app's name later, but its mount stays where it was, so the payload never derives the directory from a name: `Client.GetBackend` reads it from the same inspect that resolves the IP, accepted only directly under the resolved root, and `buildPayload` adds `socket` only when a socket inode is there. Do not rename the directory on the switch instead: that changes the path the proxy holds and costs a second `/config` push, which resets every site's TLS and OCSP caches. Cleanup is `SweepProxySockets` (first pulse with Docker, after deploys and deletes): unmounted directories past a grace period go. It reads mounts from the list API, which reports `/host_mnt/...` sources on Docker Desktop, so it counts any mount at `BackendMount` by base name and keeps on any error; making it strict would delete live directories. `ODAC_BACKEND_SOCKETS=off` turns all of it off.

## 3. Core Directives (Non-Negotiable)

### A. Performance & Scalability
- **Big-O Awareness**: Prioritize O(1) or O(n log n).
- **Concurrency Discipline**: goroutines must be tracked and stoppable; guard shared state; new tests must stay `-race` clean.
- **Memory Safety**: Close all streams, listeners, and connections. Prevent leaks at all costs.

### B. Engineering Standards
- **Toolchain Gates**: after ANY code modification run `gofmt -l .` (must print nothing), `go vet ./...` and `go test ./...` — all clean before you are done.
- **Structured Logging**: use the project's log helpers (module-prefixed lines; the watchdog adds timestamps). No stray `fmt.Println` in services.
- **Configuration**: NO HARDCODING. Use environment variables or the config store (`internal/config`). Ensure the system is "Zero-Config" where possible by inferring defaults.

### C. Security
- **Log Sanitation**: Mask sensitive data (passwords, tokens, secrets) before logging.
- **Hardened Inputs**: Sanitize and validate every input. Use secure execution patterns for shell commands.
